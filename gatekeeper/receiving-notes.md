# 受け取りの補足

CLAUDE.md「成果物の受け取りと統合」の手順を前提に、そこに書いていない細部だけを置く。

## 届き方

- **WSL機では、Hideki が zip を置いたあと自分で `! rm *Identifier` を打つ。それが「次の便が届いた」の合図**（続けて `files.zip` とだけ送ってくる）。こちらが `clean_zone_identifier.sh` を回すと「対象なし」になるのが普通で、それで正しい
- `files.zip` はリポジトリ直下に置かれる。**スクラッチパッドへ展開して読む**（リポジトリを汚さない）。中身の名前・個数は固定でない（`catalogN_M.diff`／`roundN_M.patch`、申し送りは便ごと、単体コピーがファイルでもディレクトリでも来る）
- 一つの zip に**複数の便が入ることがある**（例：`catalog45_2.diff`・`catalog45_3.diff`・`catalog45_2+3.diff`）。適用済みの便が再同梱されていたら、統合済みのものとバイト一致を確かめて飛ばす。一括版（`2+3`）があれば、前の基底の worktree に一括版を当てた結果と、こちらで順に当てた結果を全ファイル比較してから進む
- 単体コピー（`*.json`・`*_単体コピー/`）はパッチ生成物とバイト一致を確認して捨てる。zip直下の `*.json` は `.gitignore` の外なので、消さずに `git add -A` すると混入する
- **Artifact で届くことがある**（カタログ48第1便）。URL を `Artifact` ツールの `action:"read"` で読むと申し送り全文が返り、添付は `paths` に published path（`catalog48_1.diff` 等、`scope:"files"` の list で見える）を渡すとスクラッチの `artifact-files/<id>/` に落ちる。リポジトリ直下に何も置かれないので、作業用ファイルの削除は要らない
- コミット前に `git status` で作業用ファイルが stage に入っていないかを見る（`.gitignore` は `files.zip`・`*.patch`・`*.diff`・`申し送り*.md` を覆うが、別の拡張子で来れば穴が開く）

## 差し替えパッチ（補遺が同じ基底のフルパッチで来る）

前のパッチをこちらはコミット済みなので、そのままでは当たらない。revert して当て直すと履歴が読めなくなるので、増分だけを積む。

1. `git worktree add -f --detach <scratch>/wt <元の基底コミット>`
2. worktree で `git apply` して目標ツリーを作る
3. `git -C <wt> status --porcelain -z` で変更ファイルを取り、Python の `shutil.copyfile` で本ツリーへ写す
4. 本ツリーの `git diff` が増分だけになるので、補遺としてコミットする
5. `git worktree remove --force <wt>`

## 日本語ファイル名

`git diff --name-only`・`git status --short`・`git ls-files` は非ASCIIパスを8進エスケープでクォートして出す。シェルの `for f in $(...)` や `while read` に渡すと壊れる（ファイルが無い扱いになり「差分あり」と誤読する）。**`-z` で取って NUL 区切りで読む**か、`git ls-files -- '*検品*'` のようにパススペックで引く。

## 新しい assert の確かめ方（CLAUDE.md の補足）

- 正準JSONを `shutil.copy2` で退避 → 正準から作った最小変異で壊す → `restore.py` を回してメッセージを見る → 復旧して緑を再確認。未コミットの新規ファイルは `git checkout` で戻せないので、退避は自分で取る
- **件数 assert の後ろにある新 assert は、件数 assert が先に落ちて単独では確かめられていないことがある。** 件数 assert を一時的に外し、件数を保った反例（あるいは要素を抜いた反例）で、新 assert が名指しのメッセージで落ちるかを見る（カタログ45：鏡像7対の包含 assert）
- 「移設のみ・意味変更なし」を謳う再編パッチは、旧新のJSONを全葉値へ平坦化して Counter で比べる（減った値＝取りこぼしの候補）。未改修の assert が参照するキーパスが新構造でも解決するかも見る

## 散文の二次コピーの巡回（CLAUDE.md の補足）

- パッチが新設した「今回の周の段落」を最初に読み、そこに出る数字をその場で全部数え直す（いちばん当たる。正しい数はたいていパッチの中に書いてある）
- 正準JSONから件数表をスクラッチで作り、巡回先から `\d+(件|枚|軸|対|行為|スケール|糸|エッジ|門)` を文脈つきで抜いて突き合わせる。**全件表示して件別に分類する**（先頭数件で打ち切らない）
- 累計や補遺の列挙のように、パッチのたびに一つ増える自己言及は追いかけて指摘しない（一箇所に畳む裁定を促す側に回る）

## 帳簿の細部

- 作業訳を直すパッチは、JSON を全体再シリアライズせず該当行だけ置換されているか（`"NNN": "..."` は一意）。`ja_tr*.py` 側との一致は `source_sync_check.py` が見る。既知の警告3件（No.563・571 が ja_tr2/ja_tr7、No.1124 が ja_tr4/ja_tr9 に重複、値は同一）は無害
- 旧範型（`*_prototype.py`）の `DISCUSSION` は文字列（空行区切り5段落）、全数シート（`*_full_prototype.py`）は5要素のリスト。統合JSONのトップキーと `.py` の `ACT_TITLE` は表記が揺れるので、対応は推測せず表で持つ
- **レベル帯は行順で読まない。** 範型の行は口頭→書面の順で、レベル昇順ではない。`min/max(level, key=順序)` で取り、帯は「範囲＋分布の但し書き」で照合する（例：「A1〜B2、A1は書面のNo.649のみ」）。直す向きは `data/descriptors_en_1224.json` で直接引いて決める

## 教訓（受け取り）

- **zipの名前が変わると `.gitignore` の穴から混入する。** `files46_2.zip` が `files.zip` のパターンを外れて `git add -A` で入った（カタログ46第2便）。`files*.zip`・`精読用*.md` を追加して塞いだが、**コミット直前に `git show --name-only --format= HEAD` で中身を数える**のを習慣にする
- **git 2.24.1（このMac）では `git restore --staged <path>` → `git commit --amend` でツリーから落ちない。** `git status`・`git ls-files` は index から消えたと言うのに、amend で作られる木には残る（`git write-tree` も残った木を返す）。確実なのは `git reset --mixed <親コミット>` してから**意図したパスだけを明示的に `git add`** し直すこと
- **便が飛んで届くことがある。** カタログ46は 46_1（第1便）→ 46_2（補遺1）→ **46_4（第3便）** の順に届き、46_3（第2便）はあとから別名の zip で来た。番号の飛びに気づいたら、まずリモートを `git fetch` して別マシンが統合していないかを見る。累積フルパッチなら基底を worktree に出して増分を積み、**両者が重なるファイルのバイト一致**で版ずれを確かめる（カタログ46では4ファイルが一致＝ずれなし）

- 申し送りの「破壊テスト済み」「収載前の台帳で落ちることを確認」は額面で受けず、少なくとも一つは自分で再現する。自宅の別マシンが先に dry run した報告が先着することもあり、それも再現してから使う
